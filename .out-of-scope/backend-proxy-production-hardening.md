# 後端代理內建身分驗證、總用量配額、共用的速率限制與巢狀深度上限

選用後端代理（`backend/worker.js`，Cloudflare Worker 範例）維持「範例」的定位：不內建身分驗證、總用量／費用配額、跨實例共用的速率限制，也不設模型輸出的巢狀深度上限。正式部署前要自己補的項目與可以怎麼補，列在 `backend/README.md` 的「不可直接上線」。

範例本身仍然要正確：#158 修掉了速率限制的兩個小問題（過期的紀錄不清、缺 `cf-connecting-ip` 時所有請求共用 `unknown` 這個鍵），因為那是範例自己的缺陷，不是正式部署才需要的功能。

## 為什麼不做

- **網站沒有內建呼叫代理**：網站預設不需要任何 API 金鑰，案例互動展示在瀏覽器裡用示範引擎執行；README 只有前端接法的示意。沒有使用者在等它上線。
- **每一項都要先定產品決策**：
  - 身分驗證要先決定代理給誰用：組織內部（Cloudflare Access）、公開網站（Turnstile）、簽發短效權杖，還是只給操作者自己用。
  - 總用量配額要先定費用政策：每日請求數或 token 預算、超過時回 429 還是停用到隔天。
  - 共用的速率限制與配額的計數要存在哪裡（Rate Limiting binding、KV、Durable Objects），跟 Cloudflare 帳號的設定綁在一起。
- **實測要真的部署與付費的模型呼叫**：這些功能在本機的 `worker.fetch` 測試裡看不出是否真的有效，要部署到 Cloudflare、打真的模型才算驗證過。
- **巢狀深度**：#281 之後，輸出判定只沿著 schema 往下走，巢狀很深但合格的輸出不會讓判定超過呼叫堆疊，代理照原樣轉回 200。要不要擋，取決於下游怎麼處理回應；代理不知道下游是誰，所以交給部署的人決定。

## 什麼時候值得重新考慮

- 網站要內建呼叫代理（例如「用真實語言模型跑 skill」的按鈕）。
- 有人要把代理公開部署，或給組織內部的多人使用。
- 已經有人部署，並且回報了被濫用或費用失控的情況。
