# 未納入清冊的對外資產照常送往模型

送往模型前的篩選（Python 的 `scoped_files`、JS 的 `scopedBundle`）原本只留下 `asset_id` 在允許範圍內的曝險列。`asset_id` 為 null 的列（EASM 看到、清冊裡沒有的對外資產，合成資料的 `old-test.northwind-synthetic.example`）因此也被排除，提示詞寫「未確認歸屬的對外資產已於送出前排除」。

問題出在三處互相矛盾（#206，Gemini 真實模型驗收 run 42115645257、42133497099）：

- 模型收到的 `exposures.json` 只有 6 筆，區塊標題寫「腳本預先計算筆數：6」。
- 同一份提示詞的「排除前」筆數寫 7。
- 驗收第 1 項要求回報 7 筆，附加檢查還要求把它列為「未納入清冊的對外資產」並放進指標（`scoring-rules.md` 第 5 節追蹤指標第 6 項）。

模型照收到的資料回報 6 筆，兩次執行、三個變體都因此不通過。

決定：

- `asset_id` 為 null 或沒有這個欄位的曝險列，篩選時照常送出，其餘欄位不動。`asset_id` 是字串的列照舊依允許範圍判斷，空字串與範圍外資產照舊排除。
- 「什麼算未納入清冊」只有一條規則：Python 是核心的 `is_unlisted_exposure`，腳本預檢的 `unlisted_hosts` 也改用它；JS 是 `scopedBundle` 裡的同一個條件。兩邊由 `tests/fixtures/scoped-bundle-cases.json` 的共用案例守住一致（比照 ADR 0007）。
- 提示詞的腳本預檢說明改成：範圍外資料已於送出前排除；未納入清冊的對外資產照常送出，請列為資料品質的異常，並計入指標。

## Considered Options

- **維持排除，驗收改看送出後的筆數，指標由腳本算好提供給模型**：否決。未納入清冊的對外資產本身就是要回報的曝險（攻擊者看得到、防守方沒有列管）。只給模型一個數字，模型就沒辦法在報告裡說它是哪一台、有哪些問題；驗收也得在 API 路徑和對話介面路徑用不同的預期筆數，對話介面的使用者貼上的是完整檔案。
- **送出，但拿掉 hostname 與 IP，只留問題清單**：否決。要能把它納入清冊，報告就得指出是哪一台；而且這些欄位本來就是從網際網路觀察到的資料。管理摘要的遮罩規則照樣適用。

## Consequences

- 模型收到的 `exposures.json` 筆數和「排除前」筆數一致，合成資料是 7 筆，驗收第 1 項的預期不變。
- 這筆資料不屬於授權範圍內的任何資產，卻會送往模型供應商。授權範圍的篩選本來就以資產為單位（`in_scope_assets`），這筆沒有資產可以比對。它是從網際網路觀察到的結果，不是組織內部資料；如果組織的資料分類政策不允許送出，要在上傳前從 `exposures.json` 拿掉。部署指南的資料邊界那一段已寫明。
- 規則只改送出前的篩選，不改授權範圍守門（ADR 0004）與排除規則（ADR 0007）：`excluded_assets` 只列資產識別碼，比對不到 null，所以「排除優先」不受影響。
- 腳本預檢對 `asset_id` 為空字串的列，不再算成未納入清冊的對外資產。空字串是字串，照範圍規則處理，會被當成範圍外資產排除。示範引擎（`assets/demo.js`）只跑合成資料，判斷式照舊。
- 這是模型讀的文字（腳本預檢那一句），影響所有走 API 腳本與後端代理的平臺；對話介面的使用者本來就貼完整檔案，不受影響。
